# EnergyFox CRM — EC2 deploy (Docker Compose)

Single EC2 instance running the whole stack: nginx → Next.js + gunicorn/Django →
Postgres, all in Docker. Serves `http://<public-ip>` with no TLS; see
[Adding a domain + HTTPS](#adding-a-domain--https) when a domain is ready.

For the larger picture (RDS, S3 media, ALB, sizing) see `../AWS_ARCHITECTURE.md`.

## What runs where

| Container | Image / build | Published on |
|-----------|---------------|--------------|
| `nginx`   | `nginx:alpine` + `nginx.conf` | `0.0.0.0:80`, `0.0.0.0:443` — the only public ports |
| `certbot` | `certbot/certbot` | — (renewal loop; no-op until TLS is enabled) |
| `frontend`| `frontend/Dockerfile` (Next.js standalone) | `127.0.0.1:3000` |
| `backend` | `backend/Dockerfile` (gunicorn, 5×4) | `127.0.0.1:8000` |
| `db`      | `postgres:15-alpine` | `127.0.0.1:5432` |

nginx serves the frontend at `/` and proxies `/api/`, `/sys-admin/`, `/static/`,
`/media/` to Django. Only `:80` / `:443` are reachable from outside; the app ports
are bound to loopback.

Which nginx config is mounted is chosen by `NGINX_CONF` in `.env` — `./nginx.conf`
(plain HTTP, the default) or `./nginx-tls.conf` (generated by `enable-tls.sh`).

Postgres data, uploaded media, and collected static live in named volumes
(`postgres_data`, `backend_media`, `backend_static`), so `docker compose down`
and rebuilds do not lose data. `docker compose down -v` **does** — that flag
deletes the database.

## Prerequisites

- Ubuntu EC2 instance (t3.medium or larger) with the repo cloned.
- Security group inbound: **TCP 80 from 0.0.0.0/0** and **TCP 22 from your IP**
  (plus **TCP 443** once you add a domain — see below).
- The instance needs a **public IPv4 / Elastic IP**. A `172.31.x.x` address is
  the private VPC address and is not reachable from outside the VPC.

## Deploy

From the repo root on the instance:

```bash
sudo ./deploy/ec2-bootstrap.sh <public-ip>
```

That installs Docker, adds a 2 GB swapfile (the Next.js build is the memory
peak and gets OOM-killed without it on 4 GB), generates `.env` and
`backend/.env` with random secrets, points Django's `ALLOWED_HOSTS` /
`CSRF_TRUSTED_ORIGINS` / `CORS_ALLOWED_ORIGINS` at the host, then builds and
starts everything. Migrations and `collectstatic` run automatically from
`backend/entrypoint.sh` on every backend start.

Then create the first admin user:

```bash
docker compose exec backend python manage.py createsuperuser
```

The script is idempotent — re-run it after an IP change and it rewrites only
the host-dependent keys, leaving generated secrets and data alone.

## Redeploy after a code change

```bash
git pull && docker compose up -d --build
```

Only rebuilt services restart. Because `NEXT_PUBLIC_API_BASE` is left blank the
frontend resolves the API from `window.location`, so a host change needs no
frontend rebuild.

## Scheduled jobs

Install the systemd timers from `energyfox-cron.md` — `process_automation_queue`
(every 5 min) and `archive_old_leads` (nightly). Without them, timed automations
and Trash purging never fire.

## Operating

```bash
docker compose ps                     # health of each service
docker compose logs -f backend        # gunicorn + Django logs
docker compose logs -f nginx
docker compose restart backend
docker compose exec db psql -U "$DB_USER" -d "$DB_NAME"
```

The database and the TLS certificates are backed up nightly by systemd timers to
`/var/backups/energyfox` (see `energyfox-cron.md` for restore steps). Take an
extra one by hand before any migration-heavy release:

```bash
sudo ./deploy/backup-db.sh          # verified + rotated, same as the nightly run
sudo ./deploy/backup-db.sh --restore-test
```

Both backup sets sit on the same EBS volume as the data they protect, so they
cover accidental deletion and bad releases — **not** loss of the instance. EBS
snapshots (AWS Backup or a DLM policy) are what covers that, and they capture the
`backend_media` volume too, which `pg_dump` does not.

Media is on the instance disk in the `backend_media` volume. Set
`AWS_STORAGE_BUCKET_NAME` in `backend/.env` to move uploads to S3 (see
`AWS_ARCHITECTURE.md`) — worth doing before this instance is treated as
disposable.

## Adding a domain + HTTPS

TLS is terminated by the nginx container with a free Let's Encrypt certificate,
renewed automatically. Two things have to be done outside the box first:

1. **DNS** — at your registrar, add an A record for each name pointing at the
   instance's public IP (use an Elastic IP, or the record breaks on every stop/start):

   | Type | Name  | Value            | TTL |
   |------|-------|------------------|-----|
   | A    | `crm` | `<public IP>`    | 300 |

2. **Security group** — add inbound **TCP 443 from 0.0.0.0/0** (and `::/0` if you
   want IPv6). Only 22 and 80 are open on a fresh instance, and certbot's own
   validation uses port 80, so a missing 443 rule fails *after* the certificate is
   issued — the site just hangs. Verify from off the instance:

   ```bash
   curl -sS -m 10 -o /dev/null https://<domain>/health   # exit 28 = 443 still blocked
   ```

Then, on the instance:

```bash
sudo ./deploy/enable-tls.sh <domain> <email>
sudo ./deploy/enable-tls.sh energyfox.in admin@energyfox.in www.energyfox.in   # multiple names
sudo ./deploy/enable-tls.sh <domain> <email> --staging                          # dry run, untrusted cert
```

The script checks DNS resolves to this instance *before* asking Let's Encrypt for
anything (a failed validation burns one of the 5-per-hour rate limit slots), issues
the certificate over the `/.well-known/acme-challenge/` webroot, generates
`nginx-tls.conf` from `nginx-tls.conf.template`, flips `.env` and `backend/.env` to
https, rebuilds, and verifies the result from outside. Use `--staging` first if you
expect to iterate; `--force` skips the DNS precheck.

Re-running it is safe: issuance always happens on the plain-HTTP config, so a run
that died halfway (TLS config selected but no certificate, which stops nginx from
starting at all) repairs itself.

### What the switch changes

| File | Key | Becomes |
|------|-----|---------|
| `.env` | `NGINX_CONF` | `./nginx-tls.conf` (was `./nginx.conf`) |
| `.env` | `NEXT_PUBLIC_API_PROTOCOL` | `https` |
| `backend/.env` | `ALLOWED_HOSTS` | domains + IP + localhost |
| `backend/.env` | `CSRF_TRUSTED_ORIGINS` / `CORS_ALLOWED_ORIGINS` | `https://<domain>` |
| `backend/.env` | `SECURE_COOKIES` | `True` — Secure-only cookies, and HSTS on |

The frontend **must** be rebuilt for the protocol change: `next.config.ts` bakes
`NEXT_PUBLIC_API_PROTOCOL` into the client bundle at build time. The script does
this; a bare `docker compose restart` would not.

`SECURE_SSL_REDIRECT` stays off — nginx already redirects, and enabling it in
Django would 301 the plain-HTTP `/health` probe.

### Renewal

The `certbot` container runs `certbot renew` every 12h; nginx reloads every 6h to
pick up a renewed certificate. Nothing to schedule. To check:

```bash
docker compose exec nginx openssl x509 -enddate -noout \
  -in /etc/letsencrypt/live/<domain>/fullchain.pem
docker compose logs certbot | tail -20
docker compose run --rm --entrypoint certbot certbot renew --dry-run
```

Certificates live in `./certbot/conf` on the instance (gitignored, not in a Docker
volume) — include that directory in any instance backup, or you re-issue on restore.

`ec2-bootstrap.sh` is TLS-aware: if a certificate exists for the host you pass, it
keeps the stack on https instead of reverting it to http.

## Troubleshooting

| Symptom | Cause |
|---------|-------|
| Browser can't connect | Security group is missing inbound 80, or you're using the private `172.31.x.x` IP |
| `DisallowedHost` in backend logs | Host missing from `ALLOWED_HOSTS` — re-run the bootstrap script with the right host |
| API calls fail with CORS/CSRF errors | `CORS_ALLOWED_ORIGINS` / `CSRF_TRUSTED_ORIGINS` scheme mismatch (`http` vs `https`) |
| Admin login bounces back to the login page | `SECURE_COOKIES=False` missing while serving over plain HTTP |
| Login shows "Unable to reach the server" | The bundle baked in `:8000`, which is bound to localhost only. `next.config.ts` must use `??` (not `\|\|`) for `NEXT_PUBLIC_API_PORT` so an empty value survives as same-origin. Check with `docker compose exec frontend grep -rlo ":8000" .next/static/chunks/` — expect 0 |
| Frontend build killed during deploy | Swap missing — the bootstrap script adds it |
| `502` from nginx | Backend unhealthy; check `docker compose logs backend` (usually a DB connection or migration error) |
| https hangs / `curl` exit 28, but http works | Security group is missing inbound **TCP 443** |
| certbot: "Timeout during connect" / 404 on the challenge | Port 80 blocked from the internet, DNS not propagated, or nginx is on a config without the `/.well-known/acme-challenge/` location |
| nginx won't start, `cannot load certificate` | `NGINX_CONF=./nginx-tls.conf` but no certificate — re-run `sudo ./deploy/enable-tls.sh <domain> <email>`, which resets to the HTTP config first |
| Mixed-content errors, or API calls go to `http://` on an https page | Frontend wasn't rebuilt after `NEXT_PUBLIC_API_PROTOCOL=https` — `docker compose up -d --build frontend` |
| certbot: "too many certificates already issued" | Let's Encrypt rate limit (5 per domain per week). Wait, or iterate with `--staging` |
| Browser still forces https after reverting to http | HSTS is cached by the browser (`max-age` 1 year, set once `SECURE_COOKIES=True`). Clear it at `chrome://net-internals/#hsts` |
